### Hamlib バージョン管理・配布方針（2026-06-09 確定）

#### 必須バージョン
- **Hamlib 4.7 以上が必須**（FTX-1F モデル 1051 および SkyWatcher ローテーターは 4.7 以降でのみ動作）
- **4.7.2 以上を強く推奨**（4.7.2 で rigctld のセキュリティ修正2件
  — CVE-2026-54634 / GHSA-gpcq-c37x-pr4、GHSA-f72v-7gmh-m9mj — が入った。
  `send_raw` のスタック境界外書き込み・`read_string_generic` のオーバーフロー・
  rigctld の認証バイパス。NET モードで rigctld をネットワークに公開する構成では直接該当する）
- 配布バンドル（AppImage / .exe / .dmg）には必ず 4.7.2 を同梱すること

#### バンドル版 Hamlib のビルド

| プラットフォーム | ビルド方法 | PyInstaller 収集元 |
|---|---|---|
| Linux | ソースから `/opt/hamlib/4.7` にビルド | `/opt/hamlib/4.7/lib/*.so` |
| Windows | 公式 `hamlib-w64-4.7.2.zip` を展開 | `hamlib-win64\bin\*.dll` + Python bindings |
| macOS | Homebrew `brew install hamlib` | `$(brew --prefix hamlib)/lib/` |

#### バージョンアップ手順（4.7.1 → 4.7.2 で実施した手順、2026-08-06）

1. upstream のリリースアセットとソース tarball の構造が変わっていないか実際にダウンロードして確認する
   （`bindings/hamlib.swg` の有無・`hamlib_wrap.c` が含まれないこと・`include/hamlib/config.h`
   が含まれないこと・w64 zip の `bin/`・`include/hamlib/` レイアウト）。ここが同じなら CI は
   バージョン文字列の置換だけで済む
2. `include/hamlib/riglist.h` を展開して、本プロジェクトが使うモデルID
   （FTX-1=1051, FT991=1035, IC9100=3068, IC9700=3081, IC705=3085, IC910=3044）が
   変わっていないことを確認する
3. `.github/workflows/ci.yml` の `HAMLIB_VER` 3箇所（Linux / Windows / macOS）・ステップ名・
   Windows の `config.h` スタブ内の版数を置換する
4. **タグを push する**。hamlib バンドルのアップロードは
   `if: startsWith(github.ref, 'refs/tags/v')` でガードされており、`workflow_dispatch` では
   スキップされる。タグを打たない限り `hamlib-bundle` リリースのアセットは更新されない

#### in-app Hamlib アップデーター（Help > Hamlib Update…）

ユーザーが GUI からバンドル版を上書きできる仕組み。AppImage・exe・dmg は読み取り専用なのでバンドルは変更できず、代わりにユーザーデータディレクトリへインストールする。

**インストール先:**
```
Linux:   ~/.local/share/fbsat59/hamlib/
macOS:   ~/Library/Application Support/fbsat59/hamlib/
Windows: %APPDATA%/fbsat59/hamlib/
```

**起動時のロード優先順位:**
1. ユーザーインストール版（`sys.path.insert(0, ...)` で先頭に追加）
2. バンドル版 / システム版

**Windowsの追加処理**: `os.add_dll_directory(user_hamlib_dir)` が必要（Python 3.8+）。`main.py` の起動ブロックで実施済み。

**GitHub Releases アセット命名規則:**（CI が自動アップロード）

| プラットフォーム | ファイル名 | 内容 |
|---|---|---|
| Linux | `hamlib-linux-x86_64-py311-4.7.2.tar.gz` | `$ORIGIN` rpath付きポータブルビルド |
| Windows | `hamlib-windows-x86_64-py311-4.7.2.zip` | フラットレイアウト（DLL + .pyd + Hamlib.py） |
| macOS | `hamlib-macos-arm64-py311-4.7.2.tar.gz` | `@loader_path` rpath + dylibbundler で依存解決済み |

`py311` の部分は Python バージョンに応じて変化（`hamlib_info.py` の `_PYVER_TAG` で決定）。

**アップロード先は upstream ではなく本リポジトリの `hamlib-bundle` プレリリース**
（ft8lib-bundle / q65lib-bundle / ft4wsjt-bundle と同じ方式）。upstream の
`Hamlib/Hamlib` リリースにあるのはソース tarball と Windows インストーラーだけで、
上表のアセットは一切存在しない。

#### アップデーターが upstream を見ていて一度も機能していなかった不具合（2026-08-06 発見・修正）

4.7.2 へのバンドル更新作業中に発覚。`src/core/hamlib_info.py` の `HAMLIB_GITHUB_API` が
`https://api.github.com/repos/Hamlib/Hamlib/releases/latest`（**upstream**）を指しており、
`_CheckWorker._find_asset_url()` がその upstream リリースのアセット一覧から
`hamlib-linux-x86_64-py311-<ver>.tar.gz` を探していた。しかしこの命名のアセットは
本リポジトリの `hamlib-bundle` リリースにしか存在しないため、**マッチは構造上必ず失敗**し、
毎回「Pre-built package not found for this platform / Python version」に落ちていた。
つまり **Help > Hamlib Update… の「Download & Install」ボタンは一度も表示されたことがなかった**
可能性が高い（他の3つのバンドルインストーラーは最初から
`https://api.github.com/repos/JF9SOM/fbsat59/releases/tags/{tag}` を見ており正しかった。
Hamlib のアップデーターだけがこのパターンから外れていた）。

副次的に `_on_check_result()` の `version == current` も、upstream のタグ由来の `"4.7.2"` と
`get_hamlib_version()`（＝`Hamlib.hamlib_version`、実際の値は `"Hamlib 4.7.2"`）を
直接比較しており、こちらも構造上必ず不一致になっていた。

**修正**:
- `HAMLIB_GITHUB_API` を `JF9SOM/fbsat59` の `hamlib-bundle` タグへ変更
- **バージョンはリリースのタグではなくアセット名から取り出す**。`hamlib-bundle` は
  ローリングのプレリリースでタグ自体が版数を持たない。さらに
  `gh release upload --clobber` は同名ファイルしか置き換えないため、
  4.7.2 を上げても 4.7.1 のアセットがリリースに残り続ける。したがって
  「最初にマッチしたもの」ではなく **`version_key()` による数値比較で最大のものを選ぶ**
  必要がある（`select_newest_asset()`）
- `get_hamlib_version_number()` を新設し、表示用文字列から数値部分だけを取り出して比較する。
  ユーザーインストール版は再起動するまでロードされないため、判定には
  `get_user_hamlib_version()`（`version.txt`）を優先する
- **判定は「一致しないか」ではなく「厳密に新しいか」**（`is_update_available()`）。
  旧実装は `version == current` の不一致をもって更新ありとみなしていたため、
  リリース側が同梱版より**古い**場合にダウングレードを提案してしまう。この状態は
  例外的なものではなく、タグを打つ前の開発ビルド（同梱 4.7.2／リリース 4.7.1）で
  日常的に発生する。実際 4.7.2 のバンドル更新時、`workflow_dispatch` でビルドした
  .dmg を macOS 実機で開いたところ「Download & Install Hamlib 4.7.1」が出た
  （2026-08-06、実機確認で発覚）
- アセット選択ロジック自体は `hamlib_info.py` 側に置いた（ダイアログ内のメソッドのままだと
  テストに PySide6 と QThread 構築が必要になるため）。`tests/test_hamlib_info.py` が
  Qt 非依存でカバーする

**教訓**: 同種の機能（バンドルの自動ダウンロード）が4つあるのに、そのうち1つだけが
別の実装パターン（upstream API を見る）になっていた。しかも失敗時は例外ではなく
「見つかりませんでした」という**もっともらしいメッセージ**に落ちるため、
壊れていること自体が長期間気づかれなかった。同じ役割のコードが複数ある場合、
新規追加時だけでなく既存分についても、参照先・命名規則が揃っているかを確認すること。

**関連ソースファイル:**
- `src/core/hamlib_info.py` — バージョン検出・ユーザーディレクトリ・アセット命名
- `src/ui/hamlib_update_dialog.py` — ダウンロード・展開・インストール UI
- `src/main.py` — ユーザーインストール版の優先ロード・Windows DLL パス登録
- `.github/workflows/ci.yml` — 各プラットフォームのポータブルパッケージビルドと Release アップロード

#### Linux 開発環境固有: sys.path surgery

開発機（`/opt/hamlib/4.7` が存在する場合のみ）は `/usr/lib/python3/dist-packages` を `sys.path` から除去して 4.7.x を優先ロードする。

**重要**: このブロックは `os.path.exists(_HAMLIB_SITE)` でガードされており、`/opt/hamlib/4.7` が存在しない一般ユーザー環境では一切実行されない。

SoapySDR も同じ `dist-packages` に存在するため、パス除去前に `import SoapySDR` をプリロードして `sys.modules` に保持する（`main.py` の `contextlib.suppress` ブロック）。

## HamlibRotatorController — Catch-up 設計

### 仕組み
接続直後の初回 `set_position()` 呼び出し時、ローテーターは現在位置から
目標 AZ/EL へ向かって動き始める（**catch-up フェーズ**）。
この間、毎サイクル `get_position()` でローテーターの実位置を確認し、
目標との差が **5 度以内**になった時点で通常追跡（毎サイクル P コマンド送信）に移行する。

catch-up には経過時間によるタイムアウトが**存在しない**（2026-09-17 に撤廃。経緯は本節末尾
「タイムアウト機構の完全撤廃」参照）。目標に届くまで、どれだけ時間がかかろうと待ち続ける。

### 定数（src/rig/controller.py — HamlibRotatorController）
| 定数 | 値 | 意味 |
|---|---|---|
| `_CATCH_UP_THRESHOLD` | 5.0 度 | この差以内になったら通常追跡へ移行 |
| `_SLEW_SPEED_SAFETY_MARGIN` | 0.8 | 実測スルー速度に掛ける安全マージン。詳細は後述「想定スルー速度の自動計測・永続化」節参照 |

想定スルー速度自体は**固定定数ではなくインスタンス変数**
（`RotatorController._assumed_slew_deg_per_s`、基底クラス既定値2.5度/秒）に変更済み
（2026-09-17）。ローテーター機種・搭載アンテナの重さ/風荷重によって実際のスルー速度は
インストールごとに異なるため、`app_settings`に永続化した実測値で自動的に上書きされる。
詳細は後述「想定スルー速度の自動計測・永続化」節参照。

### 初回jumpの先読み（lead-time）ターゲティング（2026-09-16 追加）

**きっかけ**: 実機ログ分析（既に可視領域にある衛星へ接続した際のcatch-up）で、初回jumpが
「接続した瞬間の衛星位置」という一発きりの静的な目標を送るだけで、その後catch-up終了まで
（本ケースでは約48秒間）**Pコマンドを一切再送信しない**ことが判明した。この間も衛星は
動き続けるため、catch-up終了判定（`az_diff <= _CATCH_UP_THRESHOLD`）は「ローテーターの
実位置」対「衛星のその時点の生位置（再送信はされないが比較用には毎サイクル最新値が渡る）」
で行われ、たまたま両者がすれ違うタイミングで"catch-up成功"と判定されていた——ローテーターが
実際に衛星を捕捉して追従を開始した、という意味での成功ではなかった。

過去に「catch-up中も毎tick目標を送り直す」方式を試したことがあった
（コミット`96a630d`→3日後`c2e773a`で撤回）が、SkyWatcherバックエンドは`set_position()`
1回につき`:K1 :K2 ...`という**軸停止コマンドを含む約10往復のシリアルトランザクション**を
行うため（本ファイル該当セクション参照）、毎tick送り直すと**モーターが加速しきる前に
何度も仕切り直しさせてしまい、実効スルー速度が低下して一向に追いつけない**という問題が
過去に生じたと考えられる。

**解決策**: Pコマンドは今まで通り初回1回きりのまま、**送る先を「衛星の現在位置」ではなく
「衛星の実際の将来の経路上の、十分先の地点」**にする。

1. 接続直後、`get_position()`でローテーターの実位置を取得し、衛星の現在AZとの差
   （`az_diff`）を計算
2. `lead_s = min(_CATCH_UP_LEAD_MAX_S, az_diff / _CATCH_UP_LEAD_ASSUMED_DEG_PER_S)`
   で先読み時間を見積もる
3. `RotatorController.set_predictor()`で登録されたコールバック（MainWindow側の
   `_predict_rotator_lead()`、`SatelliteEngine.observe(norad, at=未来時刻)`/
   `CelestialEngine.observe_moon(..., at=未来時刻)`を呼ぶ）で、その未来時刻の予測AZ/ELを取得
4. 予測ELが水平線下（`< 0`）なら**動かさず**、`_last_az`をNoneのまま保持して次サイクルで
   再度この計算をやり直す（LOS直前で先読み地点が地平線を割ってしまうケースへの対策）
5. 予測ELが地平線上なら、その予測AZ/ELへPコマンドを1回送信してcatch-up開始

**なぜ速度の正確な実測が不要か**: 先読み目標地点は「衛星が実際に通る経路上の点」なので、
想定スルー速度が実際より遅い方向にさえ外れていれば（＝過大評価さえしなければ）、
ローテーターがいつ・どこまで進んでいようと、衛星自身の実位置が先読み地点へ向かって
確実に近づいてくる。catch-up終了判定は「ローテーター実位置」対「衛星の生位置（毎サイクル
最新）」なので、両者が5度以内に収束するタイミングは自動的に訪れる——想定速度の精度に
依存しない。`_CATCH_UP_LEAD_ASSUMED_DEG_PER_S = 0.7`はこの「安全に遅めの下限」として、
実機ログで観測された実測値（約1.1〜1.2度/秒）より確実に低い値を初期値として選んだ
（実運用で数回試して調整する前提。過大評価すると先読みしすぎて逆効果になるため、
上げる場合は必ず実測値未満に留めること）。

**アーキテクチャ**: `src/rig/`（Hamlib制御層）は軌道計算エンジン（`src/core/`）に直接
依存させたくないため、`RotatorController`基底クラスに`set_predictor(callback)`という
汎用フックを持たせ、実際の軌道予測はMainWindow側で注入する設計にした。コールバックは
`_rot_send()`のバックグラウンドスレッドから呼ばれる（`_doppler_cycle()`と同じ理由で、
Qtウィジェットに触れないプレーンな属性読み取りのみに限定——詳細は
`MainWindow._predict_rotator_lead()`のdocstring参照）。south-init補正
（`_apply_south_offset()`）も、`_send_to_rotator()`が`set_position()`へ渡すazと
同じ座標系になるよう、予測結果側にも同じ補正を適用している。

**スコープ**: 先読みは初回jump（`_last_az is None`）のみに適用。0度またぎでの
catch-up再突入（`crossed_zero`）には未適用（動作中の通常追尾から発生するケースで、
今回のログ分析対象だった「接続直後」とは別シナリオのため）。

### catch-up終了判定を「先読み目標」基準に修正（2026-09-16、同日追加）

**発覚した問題**: 上記の先読みターゲティングを北→南パスで実機テストしたところ、
ローテーターが先読み地点まで到達せずに手前で止まり、その後は実位置を確認しながら
少しずつ衛星を後ろから追いかける挙動になった。原因はcatch-up終了判定
（`az_diff <= _CATCH_UP_THRESHOLD`）が、**実際に送った先読み目標ではなく、
毎サイクル渡される「衛星の生位置（今現在のAZ）」**と実位置を比較していたこと。
先読み目標へ向かって動いている途中で、動き続ける衛星の生位置がローテーターの
現在位置（まだ先読み目標には遠く及ばない）にたまたま5度以内まで近づいた時点で
catch-up終了と誤判定され、そこから先は毎サイクルの通常追尾（衛星をわずかずつ
追いかける）に切り替わってしまっていた——先読みして頭出ししておく、という
本来の狙いが実質的に無効化されていた。

**修正**: catch-up終了判定の比較対象を、毎サイクルの衛星生位置ではなく
**`_last_az`（実際に最後にPコマンドで送った目標のAZ）**に変更。これにより
ローテーターは先読み目標に実際に到達するまでPコマンドの再送信なしに移動し続け、
目標到達後に初めて通常追尾（毎サイクルP送信の微調整モード）へ移行する。
タイムアウト再送信（60秒）時の再送先は引き続き「その時点の衛星生位置」のまま
（先読み予測のやり直しはしていない、未変更）。

**5度の判定軸について**: `az_diff`はAZ（方位角）のみの差で、ELは判定に含まれない
（変更前から一貫してAZのみ。仰角方向のズレは通常追尾に切り替わった後の毎サイクル
送信で追従する設計）。

### 0度またぎのcatch-up再突入にも先読みを適用（2026-09-16、同日追加）

**発覚した問題**: 上記の「catch-up終了判定を先読み目標基準に変更」を最大仰角87度の
ほぼ天頂通過パス（N→S）で実機テストしたところ、TCA直前に0度またぎが発生し
（`crossed_zero`分岐でcatch-up再突入）、その後ローテーターが「変なところで停止し、
動かなくなる」症状が発生した。ログ実測: 0度またぎ検出時（衛星az=359.4°）に
先読みなしで一発Pコマンド送信→**その後26秒間で衛星の生AZは359.4°→204.0°まで
約155度移動**（天頂通過直前はAZ変化がさらに速い）。目標（359.4°）は送信直後から
ほぼ無意味になっていたが、catch-up終了判定は「送った目標」基準（前節参照）に
変更済みだったため、衛星が偶然その目標付近を通過するという事故的な救済も働かず、
`_CATCH_UP_TIMEOUT`（60秒）のタイムアウト再送信が来るまで完全に停止したままだった。

**原因**: 初回jump（`_last_az is None`）には先読みターゲティングを適用済みだったが、
0度またぎでのcatch-up再突入（`crossed_zero`）には**意図的に未適用のまま**にしていた
（「動作中の通常追尾から発生するケースで、接続直後とは別シナリオ」との理由づけだったが、
実機検証の結果これは誤った判断だった）。0度またぎは**天頂通過に近いパスのTCA付近という、
最もAZ変化速度が速い瞬間に起きやすい**ため、先読みなしで一発だけ送る設計が最も裏目に出る
ケースだった。

**修正**: `crossed_zero`分岐も初回jumpと同じ`_lead_target()`を使うよう変更。目標地点が
水平線下の場合は初回jumpと同様に動かさず、次サイクルで0度またぎ判定からやり直す
（`_catching_up`・`_last_az`を変更しないため、次サイクルも同じ`crossed_zero`判定に
自然に再突入する）。

### 0度またぎcatch-upの「出発地点からの離脱距離」ゲート（2026-09-17 追加）

**発覚した問題**: 上記の先読み修正後、最大仰角70度のN→S・北跨ぎパスで実機テストしたところ、
北跨ぎのcatch-upが目標地点へ一気に回らず、2秒間隔の通常追尾のような「2秒動いては止まる」
動きでゆっくり目標へ向かって回り続ける症状が発生した。ログ実測: 北跨ぎ検出時
（`0.2->359.9`）に先読み先（az=359.9, el=31.4）へPコマンド送信→**わずか2秒後の1回目の
ポーリングで`caught up at rot=3.8 target=359.9`としてcatch-up終了**していた。

**原因（ユーザーの実機観察により特定）**: `az_diff`の計算（`abs(rot_az - target_az)`を
0〜180度に正規化する最短角度距離）は、**ローテーターが実際にどちら向きに回転しているかを
考慮しない**。今回のケースでは、ローテーターは出発点（az≈0.2°）から**増加方向へ**回転を
開始しており、目標（az=359.9°）へ到達するには実質ほぼ360度近く回り続ける必要があった。
しかし出発直後の実位置（rot=3.8°）は、最短角度距離の計算上は目標（359.9°）とわずか
3.9度しか離れていないと判定されてしまう（0度をまたいで隣り合っているため）——ローテーターは
まだ旅を始めたばかりなのに、「もう目標に着いた」と誤判定してcatch-upを終了し、そこから
先は通常追尾（毎サイクルP送信）の「わずかずつ追いかける」動きで、残り約356度分を延々と
移動し続けていた。北跨ぎは定義上、出発点と目標が0/360の縫い目を挟んで数値的に隣接している
ため、**catch-up開始直後は常にこの誤判定が起きうる**（時間の経過では解消しない——出発直後は
経過時間に関わらず「近い」と出てしまう）。

**修正**: 北跨ぎでcatch-up再突入した瞬間のローテーター実位置を`_catch_up_wrap_origin_az`
として記録し、**ローテーターがその出発地点から`_CATCH_UP_WRAP_DEPARTURE_MARGIN_DEG`
（10度＝到達しきい値5度の2倍、しきい値判定域と重ならないマージン）以上離れるまで**、
到達判定（`az_diff`チェック）自体を丸ごとスキップするようにした。離れたことを確認できたら
`_catch_up_wrap_origin_az`をクリアし、以降は通常の到達判定に戻る。

**時間ベースではなく距離ベースを選んだ理由**: 「北跨ぎ開始から何秒間、位置確認を止めるか」
という時間ベースの案も検討したが、実際のローテーターのスルー速度を仮定する必要があり
（想定より遅ければ誤判定が再発、速ければ無駄に待つ）、チューニングが必要な新たな定数が
増えてしまう。距離ベースなら**ローテーターの実速度に自動的に適応**し（速ければ早くゲートが
外れ、遅ければその分長く待つ）、速度の仮定が一切不要になる。

**適用範囲**: この離脱距離ゲートは0度またぎ再突入（`crossed_zero`）のみに適用され、
初回jump（`_last_az is None`）には適用されない（`_catch_up_wrap_origin_az`は初回jumpでは
常に`None`のまま）。初回jumpは出発点と目標が0/360付近で隣接する構造的な理由がないため、
この誤判定は原理的に起こらない。

### タイムアウト機構の完全撤廃・想定スルー速度の引き上げ（2026-09-17 追加）

**発覚した問題**: 上記の離脱距離ゲート実装後、通常の（0度またぎを伴わない）初回接続の
実機テストで、先読み目標が「パスの3分の1先」というかなり遠い地点になり、そこへ向かう途中で
ローテーターが数十秒間まったく進んでいないように見える症状が発生した。ログ実測（19:12:23
接続のセッション）:

```
19:12:23  initial jump to az=335.5 el=24.0        ← 先読み目標へ送信
19:13:24  catch-up timeout, retrying az=324.6      ← 60.6秒後、1回目のタイムアウト
19:14:26  catch-up timeout, retrying az=293.7      ← さらに62秒後、2回目のタイムアウト
19:14:36  caught up at rot=289.9 target=293.7      ← ここでようやくcatch-up成功
```

`_CATCH_UP_TIMEOUT`（60秒）のタイムアウトが2回連続で発動し、catch-up成立までに合計約132秒
かかっていた。

**根本原因**: `_CATCH_UP_TIMEOUT`（60秒）は`_CATCH_UP_LEAD_MAX_S`（120秒）より短い。
初期のAZのズレが約42度（`0.7 × 60`）を超えるケースでは、ローテーターが正当に先読み目標へ
向かって移動している最中に、必ずタイムアウトの方が先に発動してしまうという設計上の矛盾が
あった。

**タイムアウトはそもそも何のためにあったのか**: 先読み機能導入前は、目標が常に「その瞬間の
衛星の生位置」1点だけで、時間が経つほど確実に古くなっていく設計だった。当時のタイムアウトは
「古くなった目標を定期的に最新の衛星位置へ更新し直す」ための安全弁だった。しかし
catch-up終了判定を「衛星の生位置」基準から「送った固定目標（`_last_az`）」基準へ変更した
時点（前述「catch-up終了判定を『先読み目標』基準に修正」節）で、**固定目標である以上
ローテーターが動き続けてさえいれば理屈上必ずいつか5度以内に収まる**ようになり、タイムアウトが
本来守っていた「衛星と同方向で永遠に追いつけない」問題はすでに解消済みだった。つまり
タイムアウトは、値を今更調整する（`max(60秒, 先読み時間)`にする等）以前に、**もはや存在意義を
失っていた**。

**検討したが採用しなかった代替案**: 経過時間ではなく「一定間隔ごとの実AZの変化量」を見る
スタール（無応答）検知も検討したが、これも新たなしきい値（間隔・変化量）を必要とし、
今回と同種の誤発動を再び起こしうると判断し不採用にした。タイムアウト・スタール検知いずれも
「しきい値を外れたら介入する」という設計そのものが、**正当に時間のかかっている進行中の
catch-upを誤って妨害するリスクを常に抱える**。何もしない（＝ローテーターが実際に動いて
さえいれば無期限に待つ）方が、誤って積極的に妨害するより安全側に倒れると判断した。

**修正**:
- `_CATCH_UP_TIMEOUT`・`_catch_up_start_time`・タイムアウト再送信の分岐を完全に削除。
  catch-upは目標との差が5度以内になるまで無期限に待ち続ける
- 本当にローテーターが機械的に動かなくなった場合の復旧は、レーダー画面上でX印（実位置）が
  動かないことにユーザーが気づき、手動移動（`goto()`）または再接続（`connect()`）で
  catch-up状態をリセットする、という運用に委ねる（どちらも既存の仕組みでcatch-up状態を
  正しく初期化する）
- `_CATCH_UP_LEAD_ASSUMED_DEG_PER_S`を`0.7`→**`1.0`**度/秒に引き上げ。実測値
  （約1.1〜1.2度/秒）より依然として低い（過大評価しない）安全な範囲を保ちつつ、
  先読み距離・先読み時間を約3割短縮する

### 先読み距離の計算に「Hamlibが強制する長い方の経路」を使うよう修正・先読み時間上限を撤廃（2026-09-17、同日追加）

**発覚した問題**: 上記の離脱距離ゲート実装後もなお、北跨ぎのcatch-upが完全に詰まる
（catch-upから永久に抜けられなくなる）実機ケースが見つかった。ログ実測:

```
19:58:55  initial jump to az=0.1 el=11.4
19:58:56  caught up at rot=0.1 target=0.1 sat=360.0
19:58:56  0-degree wrap 0.1->360.0, re-entering catch-up toward az=360.0 el=11.5
（以降、アプリ終了まで58秒間、catch-up成立ログが一度も出ない）
```

**根本原因（ユーザーの指摘により判明）**: SkyWatcher実機自体は0/360度をまたいで連続回転
できるが、**Hamlibのこの機種向けバックエンドは、コマンドとして送れる方位角を0〜360度の
範囲に制限している**。出発地点と目標が0/360度の縫い目をまたぐ場合、最短経路（数値上小さい
方）を辿ろうとすると一時的に0度未満または360度超の値が必要になり、バックエンドはそれを
表現できないため、**逆方向（長い方の経路、ほぼ1周分）への回転を強制される**。これは実機の
物理的な制約ではなく、Hamlibバックエンドのソフトウェア上の制限であり、アプリ側では変更
できない。

`_lead_target()`はこれまで、出発地点と目標の**最短経路の距離**を使って先読み時間
（`lead_s = 距離 ÷ 想定スルー速度`）を計算していた。しかし境界をまたぐ場合、実際に
ローテーターが辿る経路は上記の理由で長い方（最短経路の距離ではなく`360度 − 最短経路の距離`、
ほぼ360度弱）になる。今回のケース（出発0.1度、目標360.0度）では最短経路がわずか0.1度と
計算され、先読み時間もほぼゼロ秒になり、「ほとんど今と同じ、実質動く必要のない目標」が
計算されてしまっていた。目標と出発地点が実質同じ地点である以上、離脱距離ゲート
（出発地点から10度離れるまで判定しないゲート、前節参照）が要求する「10度以上の離脱」が
永遠に発生せず、catch-upから抜け出せなくなっていた。

**修正**: `_lead_target()`内で、出発地点の実位置と目標が0/360度の縫い目をまたぐ場合
（`set_position()`の`crossed_zero`判定と同じ条件: 片方が90度未満・もう片方が270度超）を
検出し、先読み時間の計算に使う距離を最短経路ではなく**長い方の経路の距離
（`360.0 − 最短経路の距離`）**に置き換えた。この判定はローテーターの実位置と目標を直接
比較して行うため、0度またぎ再突入（`crossed_zero`）だけでなく、初回jump時にたまたま
ローテーターが境界付近に駐機していた場合にも自動的に適用される。

**先読み時間の上限（`_CATCH_UP_LEAD_MAX_S`、120秒）も撤廃**: 想定スルー速度1.0度/秒に対し
120秒では120度分しか先読みできず、境界またぎで必要になる最大約360度弱には全く足りない
（計算上、120秒の上限では今回のような境界またぎケースで先読み時間が常に頭打ちになり、
根本修正にならない）。上限の本来の目的（先読み地点が水平線下になる無駄な動作を避けること）
は、`_lead_target()`内の別の独立したチェック（予測仰角が0未満なら動かさず保留する仕組み）が
既に担っており、上限自体は不要と判断し完全に撤廃した。境界またぎの最悪ケース（ほぼ360度弱）
でも、想定スルー速度1.0度/秒なら最大で6分弱に収まる。

### 想定スルー速度の自動計測・永続化（2026-09-17、同日追加）

**きっかけ**: 上記の修正後、実機ログ（21:01接続、初回jump→catch-up成立）を分析したところ、
ローテーターが**約142〜148度を約51.8秒で移動**しており、実スルー速度は**約2.7〜2.9度/秒**
と算出された。当時の想定スルー速度（1.0度/秒）の約2.7〜2.9倍であり、「衛星追尾中の通常
モードでの想定速度としては妥当でも、catch-upの全速力移動を見積もるには遅すぎる」という
ユーザーの指摘が実測で裏付けられた。

**方針**: 実スルー速度はローテーター機種、および同じローテーターでも搭載アンテナの重さ・
風荷重によって変わるため、単一の固定定数では正しい値になり得ない。そこで
`_CATCH_UP_LEAD_ASSUMED_DEG_PER_S`という**クラス定数**を廃止し、
`RotatorController._assumed_slew_deg_per_s`という**インスタンス変数**（基底クラスの
`__init__`で既定値2.5度/秒に設定）に変更した上で、以下の仕組みで自己較正する:

1. **自動計測**: catch-up episode（初回jump、または0度またぎ再突入）が開始した瞬間の
   ローテーター実位置・時刻を`_catch_up_measure_start_az`/`_catch_up_measure_start_time`
   として記録し、catch-up終了（`az_diff <= _CATCH_UP_THRESHOLD`）の瞬間に
   `_record_measured_slew_speed()`が「移動角度 ÷ 経過時間」で実速度を算出する
   （`connect()`/`goto()`でもリセットされる、他のcatch-up状態と同じライフサイクル）
2. **安全マージン**: 実測値を`_SLEW_SPEED_SAFETY_MARGIN`（0.8）倍してから
   `_assumed_slew_deg_per_s`へ反映する。想定スルー速度は「実際のスルー速度を絶対に
   過大評価してはならない」という`_lead_target()`の前提（過大評価すると、先読み地点が
   ローテーターの実際の到達可能範囲を超え、"衛星の実軌道上の点を狙えば必ず追いつく"という
   保証が崩れる）があるため、1回の測定だけで生の実測値をそのまま採用するのはリスクがある
   （その回だけ強風で遅かった、ポーリングタイミングの関係で速めに出た、等のブレをそのまま
   信用してしまう）。まずは0.8倍で運用し、遅すぎるようなら0.9等に引き上げる方針
   （ユーザー了承済み、2026-09-17）
3. **測定を信用しない条件**: catch-up開始から終了までの移動角度が`_CATCH_UP_THRESHOLD`
   以下だった場合（出発地点がほぼ目標そのものだったケース）は測定をスキップする。
   移動距離が小さすぎると「距離÷時間」のブレが大きく、信頼できないため
4. **永続化**: `MainWindow`が`app_settings`テーブルのキー`rotator_slew_deg_per_s`に
   読み書きする。既存の`rotator_cycle_ms`と全く同じパターン（`_load_rotator_slew_speed_setting()`
   /`_save_rotator_slew_speed()`）。`RotatorController`はDBに直接触れない設計を保つため、
   `set_assumed_slew_speed(deg_per_s)`（値を注入するセッター、`set_predictor()`と対）と
   `set_slew_speed_observer(callback)`（新しい実測値が出るたびに呼ばれるコールバック登録、
   `set_predictor()`の逆方向版）の2つを基底クラスに追加し、`MainWindow._load_rotator_settings()`
   から両方を配線した。観測コールバックはローテーターI/Oのバックグラウンドスレッド
   （`_send_to_rotator()`の`_rot_send()`）から呼ばれるため、DB書き込みはQtシグナル
   （`_rot_slew_speed_measured`）でUIスレッドへ引き渡してから行う（`_rot_pos_updated`と
   同じ手法）
5. **初回起動時の既定値**: まだ一度もcatch-upが完走していない・DBにキーが存在しない場合は
   2.5度/秒を使う（ユーザー指定の初期値。実測範囲2.7〜2.9度/秒よりやや低めの安全側）

**診断ログの分離**: catch-up完了時の実測結果（出発地点・到達地点・移動距離・経過時間・
実測値・マージン適用後の値）は、`fbsat59.log`本体ではなく専用の**`rot-record.log`**
（同じログディレクトリ、`src/rig/rot_record_log.py`の`get_rotor_record_logger()`）に
記録する。`propagate=False`で`fbsat59.log`/標準エラーには一切出力しない
（`src/sdr/diag_log.py`の`get_sdr_diag_logger()`と同じ実装パターン）。catch-up中の
毎サイクルの位置ポーリング自体はログに残さない（測定に必要なのは開始・終了の2点のみで、
そもそも`app_settings`への保存も開始・終了ベースの1計算のみのため、毎サイクルの中間値を
残す必要性自体がなくなった）。

### 上記の計測ロジックに、長い方の経路を考慮していないバグ（2026-09-17、同日発覚・修正）

**発覚**: 上記の自動計測機能を実装した当日、実際に北跨ぎパスで実機テストしたところ
（ユーザー報告: 「0度を跨いだとたんに全力で反対回りを開始し、無事、目標位置に到達した」
——動作自体は成功）、`rot-record.log`と`app_settings`を確認すると次の記録が残っていた:

```
catch-up complete origin=0.0 end=337.7 distance=22.3 elapsed=81.85s measured=0.273deg/s assumed(after 80% margin)=0.218deg/s
```

DBの`rotator_slew_deg_per_s`にも`0.218`がそのまま保存されていた。

**原因**: `_record_measured_slew_speed()`は移動距離を常に**最短経路の距離**
（`abs(end-origin)`を180度以内に正規化したもの）で計算していた。しかし今回のように
`_lead_target()`が`boundary_forced`（出発地点と衛星の生位置が0/360の縫い目をまたぐ）と
判定して**長い方の経路**を先読み距離に使ったケースでは、実際にローテーターが移動した
距離も長い方（この回は約337.6度）であって、最短経路の距離（22.3度）ではない。
`_record_measured_slew_speed()`はcatch-up開始時にどちらの経路が使われたかを知らないまま
常に最短経路で計算していたため、実速度を約1/15に過小評価し（本来約4.1度/秒のところ
0.273度/秒と算出）、その誤った値がそのまま`app_settings`へ永続化されてしまっていた。
このまま次回のcatch-upで使われれば、先読み時間が実速度に対して10倍以上長くなり、
この機能を追加した目的（先読み距離を実速度に見合った適切な長さにすること）が
完全に台無しになるところだった。

**修正**: catch-up開始時（初回jump・0度またぎ再突入とも）、`_lead_target()`が使うのと
**全く同じ`boundary_forced`条件**を`set_position()`側でも算出し、
`_catch_up_measure_long_path`として記録しておく。`_record_measured_slew_speed()`は
完了時にこのフラグを見て、`True`なら`360度 − 最短経路の距離`（長い方の経路）を
実移動距離として使う。`_lead_target()`のロジックを重複させる形になるが、
`_lead_target()`の戻り値を変更する（テスト契約を壊す）よりも、同じ入力から同じ条件を
再計算する方が影響範囲が小さいと判断した。

**あわせて発覚したテスト汚染問題**: `get_rotor_record_logger()`は`platformdirs.user_log_dir()`
が返す実際のログディレクトリを使うため、`pytest tests/test_rig.py`実行時も本番実行時と
**同じ実ファイル**（`rot-record.log`）に書き込んでしまっていた。新規テストが検証用に使う
架空の数値（`origin=0.0 end=100.0...`等）が、実機テストの記録と混在してユーザーの実際の
ログファイルを汚染していた。`tests/test_rig.py`の`TestHamlibRotatorController`に
`monkeypatch.setattr("rig.controller.get_rotor_record_logger", ...)`で`MagicMock`に
差し替えるautouseフィクスチャを追加し、テストが実ログファイルに触れないようにした。

誤って永続化された`rotator_slew_deg_per_s=0.218`はDBから手動で削除し、既定値2.5度/秒に
戻した。

### `_lead_target()`が「水平線下で保留」と判定した際の診断ログ追加（2026-09-17、同日追加）

**きっかけ**: 実機テスト中、ローテーターがcatch-up完了直後に一瞬で正常動作していたにも
関わらず（`Rotator: caught up at rot=75.9 target=80.2 sat=80.8`）、直後に接続確認用の
サブプロセスがSIGSEGVでクラッシュ（`Rotator: probe subprocess crashed (signal 11)` —
ローテーターの電源を入れ忘れた状態で接続を試みたことが原因、既存の
`_probe_rotator_open()`によるクラッシュ隔離が正常に機能）、その後の再接続では
`Rotator: connected`とソフト的には成功するのに、以降ずっと
`Rotator: lead target below horizon, holding before initial jump`が出続けて
一切動かなくなる症状が発生した。

**調査の壁**: TLEから実際の衛星の仰角を再計算したところ、この時間帯は先読み時間の
上限（現在の想定スルー速度3.2度/秒台なら最大でも約110秒強）のどこを取っても仰角は
プラスのはずで、通常のジオメトリでは「水平線下」という判定にはならないはずだった。
ところが**当時のログには、`_lead_target()`が実際に計算した出発地点（ローテーター実位置）・
衛星生位置・先読み時間・予測AZ/ELのいずれも一切残っておらず**、`Rotator: initial jump`
ログも「先読み後の目標」しか記録していなかったため、原因を数値で特定する手段がなかった
（電源再投入でSkyWatcher内部の相対位置カウンターがリセットされ、`get_position()`が
アンテナの実際の向きと無関係な値を返すようになった可能性を疑ったが、確証は得られず）。

**追加した診断ログ**:
- `_lead_target()`が予測仰角<0で`None`を返す直前に、出発地点（`origin`）・衛星生位置
  （`azimuth_deg`）・`boundary_forced`・`az_diff`・`lead_s`・使用中の想定スルー速度・
  予測AZ/ELを1行にまとめて`INFO`で出力
- 初回jump成功時のログ（`Rotator: initial jump ...`）に出発地点（`origin_az`）を追加
- 0度またぎ再突入成功時のログ（`Rotator: 0-degree wrap ...`）に出発地点
  （`wrap_origin_az`）を追加

動作は一切変更していない（ログ追加のみ）。次に同じ症状が再現した際は、これらのログから
出発地点が実際のアンテナの向きと乖離していないか等が数値で確認できる。

### 異常なazimuth値からの自動復帰（2026-09-18 追加・上記「調査の壁」を実機ログで解消）

**確定した事実**: 上記の診断ログを実装した状態で同じ症状（電源オフでの接続試行 →
`_probe_rotator_open()`がSIGSEGVを吸収 → 電源投入後の再接続はソフト的に成功するが
以降`lead target below horizon, holding`が出続ける）が実機で再現し、`fbsat59.log`に
`rotor_origin=2912.7`という値が記録されているのが確認できた。この値は
**23:07〜23:50の間、アプリを何度再接続してもポートを閉じ直しても寸分違わず同じ値**
で返り続けており（`2912.7 ÷ 360 = 8.09` → `mod 360 = 32.7`）、アプリ側が計算で
作り出した数字ではなく、Hamlibの`get_position()`（`HamlibRotatorController.get_position()`、
[controller.py](../src/rig/controller.py)）が実機から読み取った値そのものだった。

**`_lead_target()`側の実バグ**: `origin`（ローテーターの現在位置）がこのように
0〜360度の範囲外だと、`az_diff`の折り返し計算（`if az_diff > 180: az_diff = 360.0 -
az_diff`）は1回引くだけでは収まらず`az_diff=-2361.0`のような大きな負の値になり、
これが`lead_s=-746.2`秒（＝衛星の12分前の位置を予測せよという意味の計算）として
そのまま`_predictor`に渡っていた。衛星の過去位置はほぼ確実に水平線下になるため、
`pred_el<0`判定が常に真になり、`_lead_target()`が`None`を返し続けて初回jumpの
Pコマンドが永久に送られない、という「調査の壁」で観測された症状と完全に一致した。

**`2912.7`の解消方法**: ユーザーが手動でgoto（az=4→0）を送信したところ、直後の
`get_position()`が`origin=0.0`（＝直前にコマンドした値）を正しく返すようになり、
以降のcatch-upが正常に動作した。これはSkyWatcherバックエンドが`get_position()`の
たびに実エンコーダを独立に読み直しているのではなく、**直近に送ったPコマンドの
目標値に基づいて内部の位置トラッキングを構築している**ことを示唆している——
つまり`2912.7`という値自体は、過去のどこかの時点（0/360をまたぐ「長い方の経路」への
強制移動が繰り返されたことによる累積回転の可能性が高いが未確証）でHamlib側に
記録された、セッションをまたいで持続する内部状態であり、新規にPコマンドを送るまで
上書きされない。

**採用した修正方針（ユーザー判断、2026-09-18）**: `get_position()`自体やその場での
即時補正コマンド送信（＝実機を自動的に動かす）ではなく、**「先読み計算」と
「スルー速度計測の起点」という、catch-up開始時に一度だけ読む2箇所に限定して、
異常値を検出したら自宅位置（AZ=0.0）とみなす**という、より狭いスコープの修正を
採用した。理由:
- `_lead_target()`内の`origin`はあくまで「先読み時間をどれだけ取るか」という
  見積もりにのみ使われ、実際にPコマンドとして送られる目標は衛星の未来位置から
  別途計算される値のため、`origin`を0と仮定しても実害なく収束する
  （本ファイル「初回jumpの先読み（lead-time）ターゲティング」節の「なぜ速度の
  正確な実測が不要か」と同じ理屈——想定スルー速度さえ過大評価しなければ、
  起点の精度は結果の正しさに影響しない）
- catch-up継続中の毎サイクル確認（`rot_az`、到達判定・スルー速度計測の**終点**）は
  対象外とした。この時点では既に実Pコマンドが送信済みで、実機が正常値に復帰している
  はずの読み取りであり、誤って0とみなす方が危険なため
- 0度またぎ再突入（`crossed_zero`）の起点（`wrap_origin_az`）も対象外とした。
  この分岐に到達する時点で既に`_last_az`が設定済み（＝直前に少なくとも1回、
  初回jumpの実Pコマンドが送信済み）であり、実機で確認できている「Pコマンドを
  1回送るとget_position()はすぐ正常値に戻る」という挙動を踏まえると、この時点で
  異常値が出る可能性は低いと判断した（実例も未確認）

**実装**（`HamlibRotatorController`、[controller.py](../src/rig/controller.py)）:
新設した`_sane_origin_az(raw_az)`ヘルパーが、`raw_az`が`[-1.0, 361.0)`の範囲外なら
`ERROR`ログを出した上で`0.0`を返す（範囲内ならそのまま返す）。適用箇所は以下の2つのみ:
- `_lead_target()`内の`origin = current.azimuth_deg` → `self._sane_origin_az(...)`
- `set_position()`の初回jump分岐内の`origin_az`（`_catch_up_measure_start_az`に
  渡り、後で`_record_measured_slew_speed()`の移動距離計算の起点にもなる）

**検証**: `ruff format`/`ruff check`/`mypy --strict`/`pytest tests/test_rig.py`
（208 passed, 13 skipped）を通過。実機での再現待ち。

## Direct モードのローテーターが Connect 直後にハングしてアプリごと落ちるバグ — 原因は接続時の複数スレッド競合（2026-09-09 実機確認・修正済み）

### 症状

SkyWatcher ローテーター（Hamlib rot model **2801** = "Sky-Watcher"）を **Direct モード**
（`rotator_settings.mode == "direct"` / COM7 / 9600）で Connect すると、数秒〜25 秒ほど
（数サイクルの `set_position` が通ることもある）でアプリが「応答なし」になり、そのまま
Windows に強制終了される。ログは `Rotator: connected` の直後（または数行の
`Rotator: set position` の後）で**トレースバックも正常終了行も残さず**途切れる。
**NET モード（ctld-launcher の rotctld 経由）では全く問題なし。** ユーザーの以前の
Ubuntu 環境では Direct モードでも動いていた。

### 切り分け（やったこと）

1. **Hamlib 単体のヘッドレステスト**（Qt なし・アプリ同梱の `libhamlib-4.dll` 4.7.2 を
   ロードして COM7 @ 9600 で `Rot(2801)` を直接叩く）→ `open` 0.28s、`set_position`
   ×10 各 50〜140ms、`get_position` ×10 各 30ms、`close` まで**完走**。シリアルトレース上も
   `read_string_generic` の待ちゼロ。→ **Hamlib の Windows シリアル層のバグでも、
   ハードでも、ボーレートでもない**（`caps.serial_rate_min == max == 9600` なので 9600 は正しい）。
2. **実アプリのプロセス確認** → ハング後に `python.exe -m src.main` が**存在しない**
   （＝ハードキルされている。Python レベルのデッドロックなら残る）。
3. **クラッシュ直前のログ**に `Rotator: initial jump` が **az 違いで 2ms 差の 2 行**。
   → `HamlibRotatorController.set_position()` の `_last_az is None` 分岐に**2 スレッドが
   同時に入っている**証拠。

### 真の原因

`MainWindow._on_rotator_connected()`（`rotator_connected` シグナルのスロット）が、接続直後に
**`_rot_busy_lock` を取らないデーモンスレッドを 2 本**起動していた:

- `_fetch_init_pos` → `rot.get_position()`
- `threading.Thread(target=lambda: rot.set_position(az, el))`

同時に追尾ティック（`_send_to_rotator` → `_rot_send`、こちらは `_rot_busy_lock` を取る）も
走る。結果、`connected` 直後に**最大 3 スレッドが同一 `Rot` オブジェクト＝同一 COM ハンドルに
同時アクセス**する。`_rot_busy_lock` は `_on_rotator_connected` の 2 本には効かないため無意味。

Sky-Watcher バックエンドは 1 回の `set_position` で `:K1 :K2 :f1 :f2 :G100 :S… :J1` と
**約 10 往復のシリアルトランザクション**を行う（write + `read_string_generic`）。これが
2 スレッド分インターリーブすると、片方の `ReadFile` がもう片方の期待するバイトを消費してしまい、
飢えた側の `read_string_generic` が `expected_len` を満たせず**無限ブロック**。SWIG 版 Hamlib は
GIL を離さないので UI スレッドごと凍結 → Windows が強制終了（トレースバックも正常終了もなし）。

**Ubuntu で動いていた理由**: 同じ競合は Linux にもあるが、Hamlib の本物の termios +
`select()`（VMIN/VTIME）では飢えた read がタイムアウトで空を返し、次サイクルで復旧する
（`Protocol error` ログが出る程度）。Windows の `lib/termios.c` エミュレーションは
`ReadFile` の部分読み取り時にタイムアウトが効かず、真のデッドロックになる。
**NET モードが無事な理由**: TCP ソケット（`settimeout(5.0)` + `recv` を握り潰し）で、
rotctld がサーバー側でコマンドを直列化するため。

### 修正（コミット `6ef5276`）

1. **`HamlibRotatorController._io_lock`（`threading.RLock`）を新設**し、`connect` / `disconnect` /
   `_send_p` / `set_position` / `goto` / `get_position` / `stop` / `park` の各シリアル交信を
   すべてこのロックで囲む。呼び出し元が何であれポート単位で直列化され、インターリーブが
   構造的に起こり得なくなる。再入可能ロックなので `set_position` が内部で `_send_p` /
   `get_position`（catch-up 判定）を呼んでも問題ない。
2. **`_on_rotator_connected()`** — 無ロックのデーモンスレッド 2 本をやめ、初期位置取得＋初回
   `set_position` を `_run_rotator_op()`（`_rot_busy_lock` を尊重する既存の仕組み）経由にする。
3. **`RadioControlWidget._on_connect_rotator()`** — `rot.connect()` をバックグラウンドスレッドで
   実行（Rig 1 Connect ボタンと同じ `Signal(bool)` + `_finish_connect_rotator` パターン）。
   Direct モードの `rot.open()` が遅延・ハングしても UI を固めない。

### 実機検証

実 SkyWatcher（Windows / COM7）に対し、**UI 側 busy-lock を一切かけず** 4 スレッド × 15 周で
`set_position`/`get_position` を同時に叩くストレステスト（実アプリの競合より過酷）→
全 120 呼び出しが 100〜500ms（他スレッド待ちの直列化）で完了、デッドロックなし、
`disconnect` までクリーン。修正前は同じパターンで確実にハングしていた。GUI 実機でも
Direct モードの Connect → 追尾がハングなしで動作することをユーザーが確認。

### 教訓

- **UI 側の `_rot_busy_lock` は「ローテーターアクセスは直列化されている」という誤った
  安心感を与えていた**。実際には `_on_rotator_connected` という別経路がそのロックを
  バイパスしており、`_rot_busy_lock` だけでは守れていなかった。ハードウェア I/O の
  排他はコントローラー内部（今回の `_io_lock`）で保証するのが正しい。
- 「Ubuntu では動いていたのに Windows で落ちる」は Hamlib の Windows シリアル層を疑う前に、
  まず**アプリ側のスレッド競合**を疑う。Windows の `ReadFile` タイムアウトの緩さは
  「元からあった競合バグを顕在化させただけ」で原因ではないことがある。
- Python レベルのトレースバックも正常終了も残さずプロセスが消える＝**ネイティブ
  デッドロック（GIL 保持のブロッキング I/O）または C クラッシュ**。py-spy の
  `dump --native` でスタックを取るのが有効（今回はログの状況証拠で確定できたため未使用）。

## HamlibNetController 実装メモ（2026-05-20 確認済み）

### rigctld 標準プロトコルと VFO 割り当て（全機種共通）

**接続時（1回のみ）:**
  S 1 Main → RPRT 0  （split ON。Main=RX(DL) / Sub=TX(UL) を確立）

**毎サイクル（1秒間隔）:**
  F {dl_hz} → RPRT 0  （Main=RX / ダウンリンク周波数。前回から1Hz以上変化した場合のみ）
  I {ul_hz} → RPRT 0  （Sub=TX / アップリンク周波数。前回から1Hz以上変化した場合のみ）

**VFO 割り当ての原則（Hamlib 全機種共通）:**
- `S 1 Main` 送信後: **Main = RX（ダウンリンク）、Sub = TX（アップリンク）**
- `F {hz}`: Main VFO（RX/ダウンリンク）の周波数を設定
- `I {hz}`: Sub VFO（TX/アップリンク）の周波数を設定（split TX）
- 各バックエンドがこの割り当てを実現する仕組みはリグ固有だが（下記参照）、結果は全機種共通

**各リグでの実現メカニズム（Hamlib ソースで確認済み）:**
| リグ | S 1 Main の動作 |
|------|----------------|
| FTX-1F | バックエンドが S コマンド引数に関わらず Main=RX を強制 |
| IC-9700 | `S 1 Main`（tx_vfo=Main）が satmode を自動 ON → satmode 時は常に Main=RX, Sub=TX |
| FT-991A | 標準 split 動作: Main(VFOA)=RX, Sub(VFOB)=TX（実機確認済み） |
| その他 Hamlib 対応機 | 同様の split 動作で Main=RX, Sub=TX |

### FTX-1F 固有の制約（Hamlib バックエンドが吸収）
- S 1 Main 応答に約150ms かかる
- F/I コマンド応答は約150ms
- **アクティブVFO切り替え（`V` コマンド）は絶対に使用禁止**。TXランプ点灯どころか、
  実機でMain/Subの役割そのものが入れ替わる実害を確認済み（2026-07-15、詳細は
  「Lock（Lボタン）— dial feedback設計」セクション参照）。ソフト側の読み戻し値
  （`f`/`i`/`v`）が正常に見えても、裏で物理的な役割が壊れていることがある
- ~~f/i（get_freq）コマンドはF/I送信直後に10秒以上かかる → 使用禁止~~
  **誤診断だった（2026-07-15訂正）**。原因はリグ側の制約ではなく、クライアント側
  `_cmd_raw()`が問い合わせ系コマンド（小文字、`f`/`i`等）の成功時応答に`RPRT`行が
  一切含まれない（`RPRT`はエラー時のみ）ことを考慮せず、無条件に`RPRT`を待ち続けて
  いたバグだった。修正済み（`_cmd_raw()`のdocstring参照）。`f`/`i`は現在、Lock
  dial feedbackで実際に毎秒利用しており、正常に動作している

### 実装上の重要事項
- set_vfo_frequencies()はバックグラウンドスレッドで実行（UIブロック防止）
- _cmd()はソケットタイムアウト10秒
- connect()時に_last_dl_hz/_last_ul_hzをNoneにリセット
- S 1 Mainは接続時1回のみ（毎サイクル送らない）
- f/iダイアルフィードバック（Lock機能）は実装済み。詳細は「Lock（Lボタン）—
  dial feedback設計」セクション参照

### send_mode_only() VFO順序の根拠

全 Hamlib 対応機共通の VFO 割り当て: Sub=TX(UL), Main=RX(DL)

**クロスバンド（satmode リグ）の正しい順序:**
```
S 1 Main  （satmode確立）
V Sub  → M {ul_mode} 0  （Sub=TX=アップリンク）
V Main → M {dl_mode} 0  （Main=RX=ダウンリンク）
```

**同バンド（satmode リグ・V/V または U/U）の正しい順序:**
```
S 1 VFOB  （通常split確立: VFOA=RX, VFOB=TX）
V VFOB → M {ul_mode} 0  （VFOB=TX=アップリンク）
V VFOA → M {dl_mode} 0  （VFOA=RX=ダウンリンク）（または V Main 相当）
```

**非satmode リグ（FTX-1F, FT-991A等）:**
```
V Sub  → M {ul_mode} 0  （Sub=TX=アップリンク）
V Main → M {dl_mode} 0  （Main=RX=ダウンリンク）
```

`send_mode_only()` は `_is_same_band` フラグで上記3パターンを自動分岐する。
S 1 Main / S 1 VFOB は `apply_transponder_state()` 内の `_send_split_init_independent()` でモード設定より先に独立ソケットで送信し、satmodeを確立してからmode・CTCSSを設定する（Direct modeと同じ順序）。`connect()` の `_init_vfo()` でも再送されるが、リグはすでにSATモードに入っているため冪等。

- リグ: Yaesu FTX-1F
- PC: GPD MicroPC2 (Ubuntu)
- Hamlib: 4.7.1-rc (2026-02-16) モデルID 1051

### モード文字列 → リグCATモード変換テーブル（2026-07-05 確定）

トランスポンダーの `mode` 文字列（SATNOGS形式）は、以下5つの独立したテーブルすべてに
登録しないとリグに正しく反映されない（`src/rig/controller.py`）:

| テーブル | 用途 |
|---|---|
| `MODE_MAP` | 汎用 Hamlib 定数（起動時に静的構築） |
| `_build_live_hamlib_mode_map()` | Direct mode の satmode/generic Hamlib 経路（旧: 3箇所に重複していたのを統合） |
| `_FTX1_MODE_CODES` | FTX-1F raw CAT（`MD` コマンド1桁コード） |
| `_FT991_MODE_MAP` | FT-991/FT-991A raw CAT（Direct・NET両方の `ctcss_method=="ft991"` 経路で共用） |
| `_SATNOGS_TO_RIGCTLD_MODE` | NET mode 汎用 rigctld（`M {mode} 0` コマンド名） |

**未登録モードは必ずFMにフォールバックすること。** Direct mode 側は元々 `.get(mode, "4")` /
`.get(mode, RIG_MODE_FM)` で徹底されていたが、NET mode 側（`HamlibNetController.send_mode_only()`
の `ft991` 分岐・汎用rigctld分岐）はフォールバックせず「両VFOとも未登録なら何も送信しない」
実装になっており、未登録モード選択時にリグが**直前のモードのまま放置される**バグがあった
（2026-07-05 修正）。`SSTV`・`SSDV`・`DOKA`・`FSK` 等、SATNOGSには存在するが本アプリの
CATテーブルには元々登録されていないモード文字列は今後も出てくるため、このフォールバックは
どちらの経路でも必須。

**FT4通話周波数の実装（`community_transmitters.json`）**: 当初 `mode: "FT4"` を使っていたが
上記5テーブルのどこにも存在せず、リグがFMにフォールバック（Direct mode）または何も送信されない
（NET mode）状態だった。FT4はUSB相当のデータモードで復調する必要があるため、`"USB-D"`
（DATA-USB相当）／`"LSB-D"`（DATA-LSB相当）を新設し全5テーブルに追加。`_MODE_INVERT`
（main_window.py）にも `USB-D⇔LSB-D` を追加し、RS-44のような反転トランスポンダーで
既存のUSB⇔LSB反転と同じ仕組みでDL/ULのサイドバンドが自動的に入れ替わるようにした。

**教訓**: 「あるトランスポンダーのモード文字列を選択してもリグの実際の動作が変わらない/前の
モードのままになる」系の不具合を見たら、まずこの5テーブルすべてに当該モード文字列が登録されて
いるか、かつNET mode側にFMフォールバックが効いているかを確認すること。

## NETモードでFTX-1のDL/ULが両方Sub VFOに誤配送されるバグ — 原因はFBSAT59ではなく
姉妹プロジェクトctld-launcherの側だった（2026-08-17 解決）

### 症状

FTX-1をNETモード（rigctld経由、`ctcss_method=="ftx1"`）でFO-29に接続し、ドップラー補正を
確認したところ、**DL（145.xxx MHz帯）・UL（435.xxx MHz帯）とも実機ではSub VFOへ書き込まれて
いた**（Main側は更新されない）。ユーザーからの報告時点で、以下が既に切り分け済みだった:
- Directモード（Hamlib in-process、rigctld不使用）では一度も発生していない
- macOS移行前（Ubuntu環境）ではNETモードでもこの問題は起きていなかった

### 誤った仮説と、それを覆した実機検証（教訓として記録）

**最初に「Hamlibのバージョンが原因」と誤って結論しかけた**。開発環境をUbuntu→macへ移行した際に
Hamlibを4.7.2へ更新していたため、①dmgパッケージ版ctld-launcher（同梱4.7.2）でも再現 → ②同じMac
上でHamlib 4.7.1のrigctldを（ctld-launcherを完全停止し）手動起動して試すと再現しない、という
2点だけを根拠に「4.7.1→4.7.2のFTX-1F backend変化が原因」と判断し、実際に公式Hamlibソース
（`rigs/yaesu/ftx1/*.c`・共有の`newcat.c`・core の `src/rig.c`/`src/misc.c`・`tests/rigctld.c`/
`rigctl_parse.c`）を4.7.1/4.7.2間で全ファイルdiffするところまで進めた（結果は「Memory mode」
関連の追加とCVE対応のパスワード認証修正のみで、VFO解決ロジック自体は1バイトも変化なし）。

この段階でユーザーから「Hamlibコアの問題とは思えない、これまで問題は起きていなかった」との
強い指摘があり、**同じ手順（ctld-launcherを完全停止して手動でrigctld起動）でHamlib 4.7.2を
試したところ、こちらも問題が再現しないことが判明**——直前の「4.7.1なら直る」という結果は
Hamlibバージョンの違いではなく、**「ctld-launcherが関与しているかどうか」という別の変数**が
たまたま同時に変わっていたことによる誤った結論だった。

**教訓**: A/Bテストで2つの環境を比較する際、意図して変えた変数（Hamlibバージョン）以外に
**同時に変わってしまっている変数がないか**（今回は「ctld-launcher経由かどうか」）を常に疑う
こと。特に「動いていた時期と動いていない時期」を比較する調査では、ユーザーが明示的に
述べた事実（「これまで問題はなかった」）が自分の仮説と矛盾する場合、仮説の方を疑うべきで、
外部ソースの差分を延々と追うより先に、比較対象自体が本当にクリーンな一変数比較になっているか
を確認する方が近道だった。

### 真の原因

姉妹プロジェクト[ctld-launcher](../ctld-launcher)（本プロジェクトのNETモードが接続する
`rigctld`を、GUIから起動・監視するランチャーアプリ）には、稼働中のrigctld/rotctldを
5秒間隔で健全性チェックする機能（`_run_health_checks`、v0.1.17でWSJT-Xハング対策として追加）
があり、これがHamlib組み込みのNET rigctlクライアント（`rigctl -m 2 -r host:port f`）を
サブプロセスとして起動し、稼働中のrigctldへFBSAT59とは**別のTCPクライアント**として
接続していた。

このクライアントは、Hamlibの汎用`rig_open()`が接続直後に自動送信する「v」(get_vfo)問い合わせを、
ctld-launcher自身のコードには一切現れない形で（Hamlibライブラリ内部の暗黙の挙動として）
発生させる。rigctldサーバー側の`rig_get_vfo()`（Hamlib `src/rig.c`）はこの問い合わせに対し、
無線機に実際に`VS;`(アクティブVFO問い合わせ)を送って結果を返すだけでなく、**rigctldプロセス
全体で共有される`current_vfo`の値をその結果で上書きする**（キャッシュ実装、Hamlib 4.7.1/4.7.2
とも同一コード）。

一方、rigctldのプレーンな「F」コマンド（VFO省略、本プロジェクトのNETモードが常用する形式）は
`rig_set_freq(rig, RIG_VFO_CURR, freq)`として処理され、`RIG_VFO_CURR`は`vfo_fixup()`では
解決されず、呼び出し元がその場の`current_vfo`へ置き換える実装になっている（`src/rig.c`確認済み）。
つまり**「F」の行き先は、その瞬間のrigctldの`current_vfo`が何であるかに完全に依存する**。

FTX-1Fはクロスバンド/split構成で継続的にドップラー追尾する際、無線機の物理的な表示VFOが
運用中にSub側を指すことがある既知のファームウェア癖を持つ（本ファイル「Lock（Lボタン）」
セクションで詳述している`VS`/`FT`コマンドの相互作用と同根）。ctld-launcherのヘルスチェックが
このタイミングに重なると、rigctldが管理する`current_vfo`が恒久的にSubへ書き換わってしまい、
以降**本プロジェクトが送るVFO省略の「F」書き込みも全てSub側へ誤配送される**——「I」（UL、
`set_split_freq`）はFTX-1F backend自体の仕様で元々Sub固定なので正しく見えるが、「F」（DL、
本来Main）も巻き込まれてSubへ行くため、結果としてDL/UL両方がSub VFOに書き込まれる、という
今回の症状に一致する。

**本プロジェクト自身は「V」/「v」コマンドを意図的に一度も送らない設計**（本ファイル「Lock
（Lボタン）— dial feedback設計」セクション参照。過去の実機トラブルで学んだ制約）だが、
**同じrigctldを共有する他クライアント（今回はctld-launcherのヘルスチェック）がそれを
送ってしまえば、本プロジェクト側の注意深さだけでは防げない**、という構図だった。

### 修正

修正はFBSAT59側ではなく[ctld-launcher](../ctld-launcher)側で行った（詳細はctld-launcherの
CLAUDE.md参照、v0.1.19）。`rigctl -m 2`（Hamlib NET rigctlクライアント経由）を使うのをやめ、
生ソケットで直接プレーンな「f」(rig)/「p」(rotator)をrigctld/rotctldへ送るだけの
`probe_daemon()`に置き換えた。Hamlibソース（`src/rig.c`の`rig_get_freq()`）を確認した結果、
`current_vfo`は読むだけで一切書き換えないことが確認できており、本プロジェクトのLock機能が
日常的に送っている「f」/「i」と全く同じ安全なコマンドである。ヘルスチェック・稼働中プロファイル
への「Test Connection」ボタンの両方をこの方式に切り替えている。

### 教訓

- 「稼働中デーモンへの疎通確認」のような一見無害な監視機能でも、それが使うクライアント
  ライブラリが接続の副作用として何を送っているかまでは意識されにくい。Hamlibのように
  複数のTCPクライアントが単一の共有リグ状態（`current_vfo`）を扱うプロトコルでは、
  ある1つのクライアントの「読み取りのつもり」の操作が、無線機の物理状態と絡んで**他の
  全クライアントの動作**に影響することがある
- 本プロジェクトが「V」を避けているという既存の防御は、**本プロジェクト自身の直接操作**
  にしか及ばない。同じrigctldに繋がる可能性のある外部ツール（GPredict・WSJT-X・
  ctld-launcher等）が同種の問題を起こしうることを、NETモード関連の不具合調査では
  今後も疑うこと
- A/Bテストで結論を出す前に、比較対象が本当に「意図した1変数だけ」の違いになっているか
  を再確認すること。今回は「Hamlibバージョン」のつもりが実際には「ctld-launcherの
  関与有無」も同時に変わっていた
